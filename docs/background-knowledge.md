# 背景知识 · 读懂 MMO Mapping 需要知道的事

> 本文给第一次接触本工具的 HR、招聘或业务同学，解释它背后的**招聘 mapping 方法**、**数据口径**和**行业背景资料的用法**。
> 工具里的公司、项目、人物全部虚构；下文引用的公开行业资料只作为研究背景，不写入任何人物事实。

---

## 1. 什么是人才 mapping

人才 mapping（人才地图）是招聘与 HRBP 的常用方法：在真正开始寻访之前，先把**目标公司 → 项目 → 团队 → 关键岗位 → 具体的人**梳理清楚，回答三个问题：

| 问题 | 对应决策 |
|---|---|
| 我们的团队缺什么能力？ | 岗位画像要不要调整 |
| 市场上谁做过这种事？ | 先研究谁、储备谁 |
| 下一步做什么？ | 补证、扩样、交给招聘同事接触，还是暂缓 |

传统 mapping 常用 Excel 完成，常见问题有三个：**结论无法回到原文**、**需求一关闭认知就丢失**、**数据病理（同名、借调、二手转述）被悄悄混进结论**。MMO Mapping 就是针对这三个问题设计的。

## 2. 核心数据模型：以「任职经历」为连接层

```
人员 ──< 任职经历 >── 项目 ── 公司
            │
            ├── 能力（挂在某段任职上，不贴在人身上）
            └── 字段级证据（每个字段一条）
```

- **能力属于某段经历**：「做过战斗主策」是 2022–2024 年在某项目的事实，不是这个人永久的标签。
- **字段级证据**：任职的项目、头衔、起止年、责任范围等，每个字段都单独记录：值、逐字引文、来源 ID、依据类型（原文明确 / 推定边界 / 未知 / 职责标准化）、时间精度和限制说明。
- **可信度来自证据链，而不是一个分数**：界面上每个 ⓘ 都可以点开，看到这个结论依据的是哪句原文。

## 3. 人审闭环：模拟抽取不等于事实

```
情报录入 → 模拟抽取 → 待审提案 → 逐字段人审 → 发布 → 查询、组织图、流向同步更新
                                              ↘ 可撤销 / 可隔离来源
```

- 当前版本**没有接入真实 AI**，抽取是确定性模拟，只识别 3 份预设材料。工具不会把模拟冒充成 AI 能力。
- 只有**已发布**的事实才会进入查询、长名单、流向和组织分析；待审、隔离、已拒绝的内容一律不计入。
- **隔离一个来源**后，依赖它的字段、查询结果和流向都会重新计算，原文不会被删除。

## 4. 人才流向的四层口径（V3.4）

人才流向图最容易出错的地方，是把「履历先后」直接当成「跳槽」。本工具把流向分成四层，只有第一层计入净流量：

| 层级 | 判定条件 | 是否计入净流入/流出 |
|---|---|---|
| **明确转岗**（绿色实线） | 有已发布事件同时关联这个人及其前后两段任职，且方向一致 | ✅ 计入 |
| **履历先后**（黄色虚线） | 只能确认两段任职的时间先后，没有明确转岗事件 | ❌ 待核验 |
| **同期跨项目** | 两段任职时间重叠，可能是借调、兼任、外包支持或记录冲突 | ❌ 单列 |
| **去向未收录** | 最近一段任职已结束，库内没有后续记录 | ❌ 不等于离职或求职 |

> 设计取舍：宁可少算，也不混算。这样可能漏掉事实存在、但事件尚未录入的转岗，换来的是净流量里每一条都经得起追问。

## 5. 真实 mapping 中常见的六类数据问题

样本人物虽然是虚构的，但每个人对应真实 mapping 工作中反复出现的一类问题：

| 问题 | 风险 | 工具的处理 |
|---|---|---|
| 职级自述与公开资料冲突 | 夸大头衔，误判层级 | 任职保持待核验，不进入查询与画像 |
| 同期兼任 / 借调 | 被误读成跳槽 | 单列为同期跨项目，不计入流动 |
| 离开后回到原公司 | 被重复计入流出、流入 | 保留完整轨迹，统计跨公司次数 |
| 外包或合作方身份不明 | 雇主归属错误 | 任职待核验，提示补充雇主依据 |
| 同名不同人 | 两个人的履历被合并 | 检出同名，禁止按姓名自动合并 |
| 二手转述来源 | 单一传闻被当成事实 | 标记二手来源，提示补充一手材料 |

## 6. 长名单 A / B / C 与反向解释

- **A 层**：满足全部硬条件，且有有效字段证据。
- **B 层**：部分满足，或责任范围证据不足。
- **C 层**：未进入 A/B，**不代表能力不合格**。

反向解释会给全库每个人列出未入选原因，分为三类：**缺证**（缺证不等于没有能力）、**已收录的责任范围不足**、**偏好未命中**（偏好只排序，不淘汰）。

原因按人去重，分母是全库人数；一个人可能有多个原因，所以各原因人数不能相加。**A 层为 0 不能证明市场没人或 JD 过严**，只能说明当前库的收录情况，以及条件组合值得和业务一起复盘。

## 7. 需求对象化：一次寻访沉淀为可复用资产

- 每个招聘需求保存为带版本号的对象（v1、v2……），修改条件时必须填写原因。
- 每次交付冻结当时的名单快照，之后来源变化只提示「历史依据已有变更」，不改写历史记录。
- 业务反馈由人工记录，系统不会从日志里推断「已采纳」或「有价值」。

## 8. 组织分析的读法

- **梯队厚度矩阵**：每个项目 × 能力域中，已收录的带组及以上人数。
- **责任层级结构**：按每个人在库内的最高已知责任范围计数。
- **重要提醒**：这些指标描述的是**我们的收录状态**，不是真实团队的编制。「样本内只有一个人」不等于现实中只有一个人；某个项目所有领域都很薄时，更可能是收录不足，应优先扩样，而不是发出单点风险告警。

## 9. 公开行业资料：背景，而不是样本事实

组织分析页内置 4 条公开资料，每条都写明「可转化为什么研究问题」和「不能推出什么」：

| 来源 | 发现 | 不能据此推断 |
|---|---|---|
| [《2025 年中国游戏产业报告》](https://jinbao.people.com.cn/n1/2025/1219/c421674-40628329.html)（人民网转述，2025-12-19） | 2025 年国内移动游戏收入占比 73.29%，客户端游戏占比 22.28% | MMO 策划的人才供给或项目人数 |
| [GDC《2025 State of the Game Industry》](https://www.gdconf.com/article/gdc-2025-state-of-the-game-industry-devs-weigh-in-on-layoffs-ai-and-more/)（2025-01-21） | 在逾 3000 名全球从业者中，11% 表示过去一年曾被裁员 | 中国 MMO 核心策划的离职率，或任何人的求职意向 |
| [IGDA《Game Crediting Standards》](https://igda.org/resourcelibrary/game-industry-standards) | 开发者可能在制作名单中被错误标注、未标注或遗漏 | 署名等于雇佣关系；未署名等于没有参与 |
| [LinkedIn《Future of Recruiting 2025》](https://business.linkedin.com/talent-solutions/resources/future-of-recruiting) | 主张基于可观察的技能评价人才，并保留人工核实 | MMO 团队的标准层级比例或市场人才数量 |

## 10. 产品红线

1. 判断和事实分开存储，研判不会进入查询。
2. 派生指标只来自已发布事实。
3. **不推断求职意向，不记录联系方式**：「强意向 / 可挖性高」这类表述会被系统拦截。
4. 缺证不等于没有；结束时间未知不等于仍在职；去向未收录不等于离职。
5. 人工发布不等于独立交叉核验：同一段文本被引用多次，仍然只算一份来源。
6. 全部数据为虚构，不加入真实公司、真实姓名或真实个人资料。
